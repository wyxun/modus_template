# FOC 框架边界与内部冗余审核

日期：2026-10-09。依据当前工作区源码、`foc-architecture.md`、模块架构参考及 embedded-coding L1.9/L1.10 审核。工作区同时有其他改动，本记录描述检查时的状态，不代表所有改动均已完成验收。

修复进展见 [边界修复记录](2026-10-09-foc-boundary-fix.md)。本文保留审核时的修改前证据，当前实现以架构文档及修复记录为准。

## 结论与范围

现有分层合理，可以继续沿用。Motor 负责运行和硬件提交，Core 负责数学控制，Observer 负责估算，Position 负责来源选择，Identify 负责辨识。主要算法已经通过纯数据交换，不需要重新建立一套框架。

但“接口没有父对象指针”与“系统边界完全闭合”不同。目前电压模型语义、采样范围、部分跨对象状态访问，以及辨识子模块对父调度对象的依赖仍需收敛。冗余主要集中在配置接线和流程协调，不在 SMO 递推历史或 Ld 采集窗口本身。

范围：当前 `foc.mk` 的 18 个 C 编译单元及相关接口、规则和测试；对未接入的控制/优化组件检查接口及接入约束，不宣称已逐项验证其数学正确性、硬件时序或性能。

## 按优先级排列的发现

### 1. P1：Observer 与 Identify 使用不同语义的电压模型

证据：`motor.c:385` 把上一份 Core `tVoltageAlphaBeta` 作为观测器模型电压；`foc_core.c:76–100` 把该量直接用于 SVPWM，没有实际母线输入。Identify 则在 `foc_app.c:469–475` 用上一份占空比和实际母线 PU 重构电压。

SVPWM 的输入实际是调制度；未裁剪且母线恰好等于电压基值时，它的数值可与电压 PU 相同。母线变化或占空比裁剪后，二者不再等价。例如同一个 0.1 调制度，在母线为 0.8 pu 时对应约 0.08 pu 的理想施加电压，Observer 当前仍收到 0.1。

影响：SMO 模型误差由系统输入边界引入，调整 SMO 参数不能完整修复；后续 Flux/EKF 也会继承这个问题。

建议：明确区分调制命令与施加电压模型。Motor 发布统一的前一控制区间理想 αβ 电压及有效性；Observer、Identify 消费同一契约，再分别映射自身输入。Core 接收母线 PU 并进行电压到调制度的转换是否同步实施，应单独确定，避免改变 PI 输出语义却遗漏增益和限幅。不要在各算法内各自补偿母线。

验收：母线变化、占空比裁剪、零输出、控制/提交失败及 k−1/k 拍配对；FLOAT/FIXED 使用相同物理语义。实测母线采样时刻、PWM 生效点、死区和器件压降仍需硬件证据。

### 2. P2：电流采样入口隐式裁到 ±1 pu，未发布裁剪状态

证据：`motor.c:95–115` 在归一化前把 ADC 差值限制为 ±COUNTS_PER_BASE；`_motor_SampleCurrent()` 随后只发布裁剪后的电流，没有原值超范围标志。

电流基值是尺度，不天然等于测量上限。当前 3.5 A 基值下，小电机通常未触及该边界，但降低基值或增加激励后，超过基值的实测电流会变成同一个 ±1 pu 值。下游无法判断是实际达到 1 pu，还是软件已经截断。现有硬件 break 保护不能替代这个数据有效性契约。

建议：把可表达范围、允许工作范围、故障阈值分开。优先保留可表达的原始归一化电流；若必须裁剪，显式发布量程/裁剪有效性并在进入模型计算前处理。`qMaxPhaseCurrent` 当前主要用于参考和配置约束，不能仅凭名称认为已经完成通用实测过流保护。

验收：基值以下、刚好达到基值、超过基值、ADC 量程端点与极性；不得因 FLOAT/FIXED 表达方式不同而改变故障策略。

### 3. P2：App 仍依赖 Motor/Position 内部运行布局

证据：`foc_app.c:526` 直接判断 Motor `eState`；`foc_app.c:360` 从 Position `tHandoff.wMaxBlendSteps` 获取启动预算。

影响：调整对象内部状态或交接实现会牵动 App。后一项还把配置一致性校验依赖于已经初始化好的可变对象布局。

建议：ALIGN 失效动作由明确的生命周期事件或所需状态快照驱动；交接预算在配置推导阶段作为纯数据形成，再校验总启动预算。可以集中几行接线，不要为每个成员增加 getter。

注意：读取 Motor 拥有的 Core 输出快照用于样本组装是允许的数据边界，不应把 `tOutput` 与 PI 内部状态一并禁止。

### 4. P2：控制失败后的观测更新策略没有闭合

证据：`foc_app.c:539–545` 在控制步骤返回后，仅凭 `ePosition == OK` 推进 Observer；`motor.c:267–276` 的 Core/PWM 失败可能已使 Motor 进入故障。

影响：故障拍仍能推进历史并发布下一份候选。当前 Motor 会安全停机，重启代次也会清历史，因此不能把它直接描述为继续带故障驱动；问题是估计有效性和故障生命周期不一致。

建议：明确采用“有效历史样本仍可完成本次估算”还是“控制失败后停止推进并使候选失效”。后一种需要同时处理候选、滤波状态和复位，不能只增加一个 if 后保留旧的有效结果。

验收：Core 失败、PWM 提交失败、位置丢失、故障后查询与重新启动。

### 5. P2：Identify 的采样已隔离，但子算法仍依赖整个父对象

证据：Rs/Ld 有独立 sample 类型；然而 `identify_resistance.h:12–23`、`identify_inductance.h:14–27` 的内部入口接收 `identify_t *`，前台 PT 还接收 Motor。所有算法状态及配置又集中声明在 `identify.h`，该头文件包含 `motor.h`。

判断：目前遵守“ISR 不读 Motor”的边界，也符合现有前台通过 Motor API 启停的约定；不能称为完全独立的辨识内核。新增算法仍会修改父头文件和调度分支，并可能通过父对象访问兄弟状态。

建议：后续新增算法时，使采集/估算内核只接受自身 state/plan/sample，返回自身结果或请求；公共调度负责活动操作、错误锁存、会话启停和结果标签。前台硬件协调可以保留少量明确调用，不必为当前 Rs/Ld 引入通用回调框架或大快照。

Ld 前台读取 Motor 的只读 limits（`identify_inductance.c:493–494`）属于能力校验，而非读取算法递推状态；可收窄到注入会话接受的能力数据，没必要机械添加一串属性接口。

### 6. P2：当前实现与架构文档已发生漂移

当前源码已经有固定 αβ 辨识、自动对齐准备、`MOTOR_ISR_IDENTIFICATION_READY` 和绕过 Position/Observer 的分支。App 前台也明确在 Rs/Ld 操作期间跳过 Encoder，不能再报告“编码器失败会阻塞当前 Rs/Ld 调度”。

`foc-architecture.md:64、75、114、144、151、171、193` 仍描述 dq 样本、速度输入或尚无无编码器辨识。新的 stationary 归档记录了方向，但验收清单尚未勾选。

建议：以当前实现更新主文档，并在相应回归完成后记录能力状态。不能用历史方案或未勾选归档推断新功能已经完成验证。

### 7. 规范差距：实际调用层次与当前硬规则不一致

embedded-coding 第 72 行要求实时路径最多 3 层，且 inline/宏也计入。当前路径至少存在 `ISR → motor_IsrControlStep → _motor_ApplyControl → foc_core_step → foc_pid_Step → foc_gain_apply`，已经超过这个要求。源码边界守卫没有检查这一项。

这是明确的规范差距，但不能仅凭源码层次断言 MCU 执行慢。应结合编译后的调用、栈和周期预算决定如何调整实现或规则；在规则未正式修改前，不可自行把数学叶函数排除来宣称合规。不要为了缩短层次把所有公式重新塞回 Motor。

## 各模块的内部设计与冗余判断

| 模块 | 当前边界判断 | 内部冗余 / 建议 |
|---|---|---|
| App | 组合、接线职责合理；少量内部状态访问未隔离 | Init 的配置绑定、组合初始化和预算校验集中；可按这三个动作整理，保留集中接线，避免增加中转对象 |
| Motor | 不调用具体观测算法，拥有采样、生命周期和 PWM 合理 | 文件较长但包含多个必要运行状态；共享采样/Core/提交路径已抽取。优先统一 Start/Stop/Fault 的清理契约，不应继续拆成大量小文件 |
| Startup | 只生成强拖轨迹，职责清楚 | Q16 角步进余数与 Q31 速度累计处理不同精度需求，不是重复物理单位；暂不删除，简化需逐拍误差证据 |
| Position | 位置转换、资格和切换集中，职责合理 | 静态绑定的 `pSensorState` 与回退 `tSensor` 为头文件布局一致而共存（header:111–114），是可整理的绑定复杂度；先统一构建宏可见性，再减少双重表示 |
| Position 的 SMO 策略 | 算法证据与接管判断分开，正确 | `motor_position.c:79–85` 重复有限性检查可合并；第 96 行滤波系数 0.02 应明确对应周期，换 HF 频率时在初始化推导所需系数 |
| Encoder | 前台硬件读取、双缓冲发布、ISR 缓存读取合理 | 历史原始角用于差分，发布角用于消费，不是重复缓存；需维持时间戳和过期判断 |
| Observer | 独立算法类型与编译期组合，边界清楚 | 当前约 99 行，不需要再增加统一 vtable 或输出缓存。双算法失败状态尚未实现，属于扩展前置条件 |
| SMO | 模型/输入/状态/输出独立，公式与初始化分开 | `d_prev`、`z_prev` 是不同递推历史；两个轴状态必要。初始化的定点范围与溢出检查不能按行数视为冗余 |
| Identify 调度 | 操作选择、准备与 PU 结果发布合理 | 父/子依赖仍较强，优先让算法内核缩小参数范围；固定轴准备只服务 Rs/Ld，不能强制未来 Flux 也静止注入 |
| Rs | αβ 电流、实测母线重构电压、差分估算，单位边界合理 | 两档均值和差分是公式所需；前台阶段与 ISR 采样状态不能简单并为单一标志 |
| Ld | plan/capture/flow/result 分组合理，内部 PU | 正负半周期累计、首末电流、窗口均值和发布标志分别服务不同估算/并发需求，不能移入文件 static。日志开关下重复安全校验有维护成本，可保留一套共同判定、日志仅格式化原因 |
| Core | 数学运算、PI、调制与硬件提交分离，正确 | 体量适中；电压模型和最终矢量限幅/抗饱和反馈需要闭合。当前 `bVoltageLimited` 是判据，不能称为已经实施最终矢量缩放 |
| PID | 纯数值输入、实例状态，无父模块依赖 | PID 的微分路径在当前 PI 场景系数为零，是否值得专用 PI 取决于测得成本；不为少量代码复制两套积分/Track 实现 |
| Modulation | 纯数学与电压重构，边界合理 | `spwm/svpwm/third_harmonic` 共用基础实现合理；调制命令与模型电压必须明确不同语义 |
| Math / Numeric / Angle | 数值表示、增益、角度与坐标类型可复用 | 检查及宽位运算是数值安全需要；不能通过更改饱和语义来“简化”公式，FLOAT/FIXED 均需回归 |
| Port / target adapter | 原始 ADC、占空比、安全输出的语义 API 合理 | 当前不是全部可观测时序契约：母线时间戳与实际 PWM 生效区间仍需目标适配证据 |
| Debug | 诊断与正式控制区分必要 | 波形可以白盒读取；会改变控制状态的命令必须走语义 API。日志清理正在独立进行，本审核不改动该工作 |
| 未接入控制/优化组件 | 不在当前 foc.mk 的执行链 | 不计为当前 ISR 开销，也不因未使用直接删除；接入前另审单位、数值和编译期绑定 |

特别说明：未接入的 `foc_controller_if_t` 使用运行时函数指针，不能直接作为当前实时框架的默认接入方式；`foc_pll.c:62` 把 `qSpeed` 直接加到角度，实际隐含 turns/step，而头文件只称“速度输出”，不能不经尺度定义就接到电角速度 PU。它们是接入前需要处理的契约问题，不是当前 SMO 路径的问题。

## 建议推进顺序

1. 统一前一控制区间电压模型及有效性；明确电流测量范围、裁剪和故障契约。
2. 收敛 App 对运行成员的访问，确定控制失败后的观测处理策略；同步主架构文档。
3. 在现有文件内整理配置推导和共同判定，减少重复分支；不增加通用接口层。
4. 扩展新辨识/观测算法时缩小算法内核依赖，分别维护旧算法回归。
