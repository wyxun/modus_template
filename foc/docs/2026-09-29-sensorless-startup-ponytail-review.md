# 强拖启动与 SMO 接管的简化审查

审查范围：`a17014088a53b96e7` → `9acf1bc32ca6be13f0`，重点是强拖启动、位置接管，以及以后接入其他融合算法的成本。对照了 [`2026-09-26-sensorless-if-startup-smo-handoff-plan.md`](2026-09-26-sensorless-if-startup-smo-handoff-plan.md) 和当前代码。这是静态审查；没有运行构建、主机测试或带电实验。提交计划已明确写出未完成台架验收，本文也不把代码状态当成实机结论。

## 结论

**外层边界值得保留，内部实现偏复杂。** `Motor Prepare → Position 选角 → Motor Control → Observer 更新` 保住了单次电流采样、唯一电角反馈和 Observer 的一拍延迟；强拖失败超时、角度渐进修正和失效停机也有实际安全用途。无需为了将来算法重写这一条 ISR 主链。

复杂度主要来自两套强制角轨迹、两处启动期限、三层重复配置，以及把 SMO 专属资格判断直接放进 `motor_position_t`。因此**同一条最终反馈接口可继续用**，但“换一个估算器就沿用同一套融合实现”目前不成立。不要预先建立通用融合框架；第二个真实来源出现时，再抽取确实共用的候选归一化和角度交接逻辑。

## 相对基线增加了什么

| `a170140` | `9acf1bc` | 判断 |
|---|---|---|
| Motor 原有固定频率强制角，Position 在 SENSOR/HARD_DRAG 中二选一；SMO 仅作影子估算。 | 新增 `motor_startup_t` 的 I/f 斜坡、无感对齐入口和电流到速度模式交接。 | 启动斜坡和安全边界是需求所需；旧固定频率路径因此成为需要明确去留的并行实现。 |
| Position 直接返回传感器或强制角反馈。 | Position 增加 SMO 滤速、资格窗口、BLEND、ACTIVE/LOST 事件。 | 接管状态必要；SMO 指标和通用选角策略混在一个对象里。 |
| App 只编排采样、位置和控制。 | App 新增跨 Motor/Position 参数联动校验和事件转送。 | ISR 顺序仍清楚；配置边界变宽。 |

## 具体问题，按优先级

### P1：两个“强拖最长时间”计数，所有权和停止条件重复

`motor.c:313-320` 在电流模式下用 `wSensorlessRunSteps/wStartupMaxRunSteps` 限时；`motor_position.c:257-292` 又用 `wForcedCount/wMaxForcedSteps` 限时。App 在 `foc_app.c:375-387` 验证两者与斜坡、资格、融合窗口的关系。默认两个上限都为 60000 步，但配置允许分开改，故障首先由谁触发会随配置变化。这个重复状态还让 Position 必须知道“强拖最长多久”这一 Motor 启动生命周期条件。

**建议：** Motor 保留一个从进入 RUN 到接管完成的总体启动期限，Position 只维护资格和交接计数。Position 的 `FAILED` 用于观测器失效和融合失败；总体超时由 Motor 统一锁存位置故障。这样可删一份计数、配置及 App 的跨对象算术校验。保留超时保护本身。

### P1：BLEND 的配置步数不是实际最长期限

`motor_position.c:121-154` 同时维护按 `wBlendSteps` 增长的速度权重和每拍最多 0.5 电角度的角度修正；只有权重完成**且**角度差在本拍完全修正时才发 `OBSERVER_ACTIVE`。例如测试设置 `wBlendSteps=4`，初始角差约 11.25°，实际要约 23 拍才能完成角度修正。`foc_app.c:375-387` 却用配置的 `wBlendSteps` 判断总期限是否足够，不能证明最坏情况下有足够交接时间。

**建议：** 明确 `wBlendSteps` 是最短融合步数，并用总启动期限约束实际融合；或者改成单一、可证明在指定步数内完成的融合轨迹。对真实变化的强制角和估算角验证每拍角度、速度及完成时间。当前测试循环最多允许 100 拍，容易掩盖“4 拍”与实际耗时的差别（`sensorless_position_handoff_test.c:74-90`）。

### P1：计划要求的资格条件未全部进入判据

计划 Task 3 要检查“电流/电压限幅”。实际 `motor_position_sample_t` 只有 αβ 电流、上一周期电压模型、强拖候选和运行代数（`motor_position.h:33-39`）；`_motor_position_ObserverQualified()` 只检查 SMO 有效性、反电势强度、速度及角差（`motor_position.c:36-75`）。因此进入限流或调制饱和时，资格窗口仍可能累计。主机测试通过也不能证明该工况可安全接管。

**建议：** 在实机启用自动接管前，确定限幅/饱和是否必须阻止接管，并用一次明确的状态输入和测试落实；若实验表明不需要，修改计划，避免文档承诺与代码不一致。此项是验证缺口，不能靠删减代码解决。

### P2：旧固定频率路径与新斜坡路径并存

`motor.c:335-350` 按 `bSensorlessStart` 在 `motor_startup_IsrStep()` 和原有的 `tHardDragAngle/wHardDragAngleStepBam32` 之间分支；对应配置同时保留 `nHardDragElectricalMilliHz` 和 `wStartupRampSteps`（`motor.h:62-66`）。两条路径最后都产生同一种 `tHardDragCandidate`。旧路径在测试中仍有使用，因此现在不能无证据直接删除。

**建议：** 明确固定频率实验是否仍是产品能力。若是，让同一个轨迹组件支持“斜坡步数为零时保持固定频率”，统一输出；若不是，在确认外部调用后删除旧路径及配置。不要为将来的任意轨迹预建策略表或函数指针。

### P2：SMO 专属规则锁进 Position，复用范围窄于计划描述

`motor_position.c:36-75,157-205,208-296` 直接读取 `tObserver.tOutput.qSignalStrengthPu`、原始 SMO 速度和一拍预测角；`motor_position.h:69-77,94-118` 固定存放反电势门槛、滤速、强拖资格、融合修正、事件等状态。`foc_observer.h:14-32` 目前也只容纳 SMO 配置及实例。这对当前“强拖 → SMO”足够，但 HFI 的低速资格、磁链模型的置信度、Encoder/SMO 联合选角不能直接共用这些判据。

**建议：** 保留 `motor_electrical_feedback_t` 和 ISR 调用顺序。将来接入第二种估算器时，让其先产出相同量纲的候选角/速度/有效性，再在 Position 内为该来源实现自己的资格判断；仅当两条实际路径出现相同交接代码时，才抽出角度限速和状态迁移。当前不需要注册表、统一 `void *` 算法接口或运行时多态。

### P2：配置跨三层转抄，新增算法会继续膨胀

`motor_config.h:33-46` 定义接管宏；`foc_app.h:31-41` 和 `foc_app.c:27-40,411-425` 再复制到 App 配置；`motor_position.h:66-77` 再复制到 Position 配置；`motor_position.c:330-349` 再复制到运行对象。多个字段只是传递，没有在 App 层形成新的业务含义。下一套算法照此做会增加宏、结构体成员和 Init 赋值的改动面。

**建议：** 保留编译期默认值，但用一个 Position 接管配置子结构体在 App 边界传递；Position 初始化时只保留运行期真正需要的预计算值和门槛。先消除重复转抄，再考虑是否拆模块。不要仅为减少成员数增加 getter/setter。

### P3：底层轨迹支持负速，但公开无感启动只允许正速

`motor_startup.c:45-48` 和 `sensorless_startup_test.c:45-53` 支持负速；`motor.c:588-593` 的公开入口明确拒绝负速，计划 Task 2 也限定正向。负速分支目前只在底层独立测试里可达，增加了当前需求不使用的范围。

**建议：** 在确定需要反转启动前，统一按正向契约实现和测试；若保留负速用于固定频率实验，应把它标成该实验路径的能力，避免误以为完整无感反转已受支持。

### P3：现有架构文档已落后于代码

[`foc-architecture.md`](foc-architecture.md) 仍称“无感接管和角度融合未实现”，且图中 Observer 在 Position 选角前更新；现代码在控制/PWM 之后更新 Observer，下一拍消费估算值（`foc_app.c:769-789`）。这会误导后来实现其他融合算法的人对时序和数据新鲜度的判断。

**建议：** 在实现稳定后更新该文档的现状、时序和一拍延迟说明。未来接口设计以可执行代码和实测时序为准。

## 对后续融合算法的适用性

| 场景 | 当前外层接口是否够用 | 仍需增加的能力 |
|---|---|---|
| 强拖 → 磁链或 EKF | 角度/速度最终输出接口够用。 | 估算器输入、质量指标、资格阈值和延迟补偿须按算法确定。 |
| Encoder + SMO 融合 | 最终输出接口够用。 | 现在 SENSOR 分支直接返回，不走融合状态；需要实际的双候选策略。 |
| HFI → SMO | 最终输出接口够用。 | HFI 注入和同步采样是新的执行链路，不能塞进当前 `motor_position_sample_t` 后假装已支持。 |
| 多估算器并行仲裁 | 只保留最终反馈接口。 | 需要明确候选所有权、时序、资格和故障优先级；到真实需求出现时再设计。 |

## 最小整理顺序

1. 先补齐接管资格与融合耗时的可观察证据；自动接管维持默认关闭，待台架重复验证。
2. 统一启动总期限；决定旧固定频率路径去留，优先减少 Motor/Position 的重复状态。
3. 收拢接管配置，更新架构文档；保留当前清楚的 ISR 顺序与唯一反馈类型。
4. 第二个估算器真正接入时，再抽取共用的候选转换和交接代码。不要先做通用融合框架。

按 Ponytail 标准，预计可消去约 **80～150 行**重复配置、计数与轨迹分支，但这只是静态粗估；能删多少取决于固定频率实验路径是否继续保留。安全停机、输入校验和最小主机验证不在删减目标内。
